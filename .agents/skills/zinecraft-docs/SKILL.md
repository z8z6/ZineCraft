# Zinecraft 教程文档

为 `docs/guides` 编写可操作、可验证的开发教程。教程必须回答“它是什么、为何这样设计、代码实际上如何运行、如何使用、如何确认结果”，而不是只罗列 API 或复述源码。

## 先确定事实依据

1. 阅读仓库根目录 `AGENTS.md`、`docs/README.md`、同分类下最接近的现有教程，以及主题对应的领域 skill。
2. 用 `rg` 沿真实调用链取证：注册或配置入口 → 数据结构 → 算法实现 → 校验器 → 导出或加载 → 运行时消费者 → 测试。
3. 技术行为以当前源码和测试为准。字段出现在 Builder 或配置类中，不代表算法已经使用它；必须找到读取位置后再说明其效果。
4. 明日方舟的名称、设定、描述和美术素材遵循仓库指定的官方、PRTS 与游戏数据来源，不自行补写设定。技术流程图可以根据源码自行绘制。
5. 区分以下三类陈述：
   - **实现事实**：能由代码、测试或生成产物直接证明。
   - **设计意图**：能由注释、约束、评分项或整体结构证明。
   - **合理推断**：无法直接证明时明确写成“可以理解为”或“从实现推断”，不能伪装成既定事实。

若文档主题属于城市、生物群系、结构、维度等已有领域，必须同时使用对应的 `zinecraft-*` skill；本 skill 只规定教程的写法和站点集成方式。

## 组织教程

第一段先给读者完整心智模型，然后再展开局部实现。推荐结构如下，可按主题删减，但不能跳过读者完成任务所需的关键内容：

1. 目标、适用范围和最终产物。
2. 核心术语与数据层级。
3. 从输入到运行时结果的总流程。
4. 每一个算法阶段的设计意图、实现和算例。
5. 配置或扩展示例。
6. 校验、调试与常见失败。
7. 源码索引和进一步阅读。

标题必须是唯一、面向任务的一级标题。避免把教程写成逐文件的代码导览，也不要复制大段源码；只保留帮助理解契约和扩展点的最小代码片段。

## 解释算法

首次使用 Voronoi、Delaunay、松弛、包围盒、拓扑、候选边等术语时，先用直观语言定义，再给数学表达。不要假设读者已经知道计算几何术语。

每个算法阶段至少说清：

- 输入和输出分别是什么。
- 这一阶段解决什么问题，为什么不能省略。
- 当前实现按什么顺序执行，包括循环、排序、裁剪和失败分支。
- 使用的公式、每个符号的含义、单位、取值范围和边界条件。
- 一个带具体数字或坐标的完整算例。
- 哪些约束由校验器保证，违反后会发生什么。
- 对应的核心源码和测试文件。

数学符号和公式优先使用 LaTeX。当前站点通过 `remark-math` 与 KaTeX 渲染：行内公式使用 `$...$`，独立公式使用 `$$...$$`。例如：

```markdown
点 $p=(p_x,p_z)$ 到站点 $s_i$ 的欧氏距离为：

$$
d(p,s_i)=\sqrt{(p_x-s_{i,x})^2+(p_z-s_{i,z})^2}
$$

Voronoi 单元定义为：

$$
V_i=\left\{p\in\Omega\mid d(p,s_i)\le d(p,s_j),\ \forall j\ne i\right\}.
$$
```

公式后紧接符号表或逐项解释，不能只给公式。复杂推导使用 `aligned`、`cases` 或 `alignedat` 环境保持等号对齐；集合、范数、向量、上下标和分式使用标准 LaTeX 命令，不用 Unicode 上标或空格手工模拟排版。流程、伪代码、坐标图和目录树仍使用代码块或 SVG，不要硬塞进数学环境。涉及随机数时说明种子来源和确定性；涉及世界生成时说明既有世界、数据包重载和新生成区块各自是否受影响。

## 记录配置的真实状态

配置表至少包含名称、默认值、单位、约束、作用阶段和当前状态。当前状态使用明确措辞：

- **参与计算**：算法读取并影响结果。
- **仅导出元数据**：写入产物但当前几何或运行时不消费。
- **预留**：API 已存在但尚未接入。

不要把预留字段描述成已经生效。配置之间存在联动时给出约束关系和失败示例，例如最小值不得超过最大值、区域数量必须覆盖必需角色等。

## 编写示例

示例应从仓库现有声明中选择最接近的模式，并保持注册 ID、命名空间和目录约定稳定。一个完整示例需要包含：

1. 最小可运行配置或代码。
2. 输入值如何经过算法转换。
3. 预期生成的数据或可观察结果。
4. 一种常见错误及其修正。

明确区分手写文件与数据生成器产物。生成文件应修改其源配置并重新生成，不能指导读者直接维护生成结果。

## 绘制有效的图

当流程包含至少三个阶段、多个分支或难以用一段文字说明的空间关系时使用图示。图必须表达数据变化、判断、循环或空间关系，不能只是装饰性方框。

当前教程站点解析 GFM 和 LaTeX，但不解析 Mermaid。复杂图使用原生 SVG：

- 文件放在 `docs/public/diagrams/<descriptive-name>.svg`。
- Markdown 中使用 `![准确的替代文字](./diagrams/<descriptive-name>.svg)`。
- SVG 提供 `role="img"`、`<title>` 和 `<desc>`，使用 `viewBox`，保证窄屏缩放后仍可读。
- 用箭头、编号、图例和一致的颜色区分阶段；颜色不是唯一的信息载体。
- 空间算法应同时画“几何直觉图”和“数据流程图”，必要时用小坐标算例连接两者。

小型关系可用表格或 ASCII 图，不必为每个概念创建 SVG。涉及明日方舟世界观的插画优先复用仓库指定来源，不用生成式图片代替原始资料。

## 接入教程站点

- 教程放在 `docs/guides/<category>/<slug>.md`；站点通过 `import.meta.glob(''../guides/**/*.md'')` 自动收录，无需维护手工索引。
- 一级标题决定显示标题；目录名决定分类；文件名决定稳定路由。
- 优先使用现有分类：`overview`、`item`、`block`、`entity`、`world`、`combat`、`skill`、`collectible`、`modeling`、`interface`。不要依赖未知分类自动回落到 `world`。
- `docs/public` 会复制到站点根目录，因此教程中的图使用 `./diagrams/...`。
- 源码链接沿用现有相对路径风格，并确认目标真实存在。站点会把指向 `src` 的链接转换为 GitHub 源码链接。
- 本地命令从 `docs` 目录执行：`npm run dev` 用于交互预览，`npm run build` 用于完整构建。
- 直接预览目标页时使用 `#/doc/guide/<category>/<slug>`，并检查刷新后仍能加载。

可参考 `docs/guides/overview/content-workflow.md` 的任务式表达，以及 `docs/guides/world/add-nation-city-region.md` 的算法、公式、算例和图示组织方式，但必须重新核对当前源码，不能把旧教程当成实现事实。

## 工作流

1. 先执行 `git status --short`，识别并保留用户已有改动。
2. 列出需要回答的读者问题，并为每个关键结论找到源码或测试证据。
3. 先写术语、总流程和算法阶段，再补配置与操作步骤，避免形成只有步骤、没有原理的教程。
4. 为抽象阶段加入数字算例；为复杂流程或空间关系加入图示。
5. 逐条回查字段读取点、默认值、单位、失败条件和链接目标，特别标记未接入的 API。
6. 执行站点构建和静态检查；只有实现代码同时变化时才运行对应领域 skill 要求的 Java 或数据生成验证。

## 验证

至少执行：

```powershell
git diff --check
Set-Location docs
npm run build -- --logLevel error
```

对新增 SVG 使用 XML 解析器检查格式，并确认构建后出现在 `docs/dist/diagrams`。同时检查：

- Markdown 代码围栏成对闭合，标题层级没有跳跃。
- 新教程被构建产物收录，分类、标题和 hash 路由符合预期。
- 源码链接、图片路径与示例中的注册 ID 均真实存在。
- 公式在纯文本情况下可读，符号全部定义。
- LaTeX 使用 KaTeX 支持的语法，构建日志中没有数学解析错误；长公式在窄屏下可以横向滚动。
- 文档没有声称未被消费的字段会影响算法。

若 `npm run dev` 报 React effect 返回 Promise，检查 `docs/src/App.jsx` 中的 `useEffect`：effect 本身只能返回清理函数，异步工作应放在 effect 内定义的异步函数中再调用。修复站点代码属于独立变更，必须在交付说明中与教程内容分开列出。

交付时简要列出新增或修改的教程与图、验证命令及结果、已有但与本任务无关的警告，以及尚未实际浏览器确认的部分。
